01 — Context

The Challenge

The Customer Portal is the operational backbone for both internal teams and external stakeholders — used daily for data management, survey configuration, program tracking, and reporting. Despite its critical role, recurring support tickets and qualitative feedback pointed to one root cause: the navigation experience was creating constant friction.

The executive goal was clear: transform the portal from a tool people grudgingly use into one they can move through efficiently — removing navigation hurdles and streamlining core workflows.

03 — Research

User Interviews

To understand how users actually move through the portal day-to-day, we conducted qualitative interviews. Users are predominantly power users — subject matter experts who switch between many modules repeatedly throughout the day.

"

I have to shuffle between more than 8 modules almost every day. I basically switch about 50 times a day.

"

As a subject matter expert on Metrics, I only use the Programs List — but I have to go back and forth setting up a metric that requires Program Areas and Items.

"

I've written down all the modules and their paths so I don't waste time navigating.

"

Key insight: users had developed workarounds (notes, bookmarks, multi-tabs) just to survive the navigation — a clear signal the system was broken.

04 — IA Redesign

Information Architecture

The existing IA relied on a hierarchical drill-down pattern originally designed for new and infrequent users. As the module count grew, this created compounding friction. We collected every module and sub-module, then used reverse card sorting with stakeholders to reorganize everything into a 3-level persistent structure.

Access patterns and roles were carefully factored in — different user groups see different modules based on their permissions. A collaborative spreadsheet kept stakeholders aligned throughout.

06 — Design Decisions

Trade-offs & Decisions

Three major tensions surfaced during the design process, each requiring negotiation across product, engineering, and ops leadership.

⚡
Speed vs. Learning Search-first vs. Nav-first ▾

Product wanted to hide the navigation tree and make search primary — fastest for existing users. Ops leadership insisted new hires needed to learn the IA structure to reference it in support tickets.

Decision: Dual-mode navigation with a 3-character minimum for search. This forced some engagement with the nav tree while keeping power users efficient. Validated: ~2s added to power user workflows, but new hire onboarding reduced by 40%.

✓ 3-char minimum · dual-mode nav
📐
Screen Real Estate vs. Persistent Visibility 280px sidebar vs. collapsed ▾

On a 1920px screen, a 280px sidebar uses 15% of horizontal space — significant for users working with dense data tables. Engineering proposed defaulting to a collapsed sidebar.

I pushed back: users were already struggling with 20+ clicks per task. Adding 2 more clicks to expand/collapse — done 50 times/day — compounds the problem by 100 extra clicks daily.

Compromise: A 'slim mode' (64px icon-only sidebar) users can toggle. Analytics post-launch: 73% kept it expanded, validating the expanded default.

Business case: the 88% productivity gain outweighed the 15% screen cost by ~$500K annually.

✓ Slim mode toggle · expanded by default
🗓
Timeline vs. Scope V1 core vs. full feature set ▾

Leadership wanted this shipped before Q4 onboarding of 20 new ops members. Engineering estimated 6 weeks for core nav, 12 weeks to include power-user features (favorites, recents, keyboard shortcuts).

Approach: Advocated for shipping V1 with just improved IA + search, but negotiated a committed V2 roadmap 6 weeks post-launch.

V1 shipped on time. V2 scope was shaped by actual usage data — we discovered users didn't want favorites, they wanted recently used modules instead.

✓ V1 on time · V2 data-informed

07 — Visual Design

Hi-Fidelity Mockups

The redesigned navigation features a 3-level persistent sidebar with integrated search. Search activates at 3 characters minimum, returning a focused result set. Each result displays the full navigation path — helping users orient themselves within the hierarchy.

The landing page copy reads "Please select a module" rather than "Please search for a module" — a deliberate choice to encourage users to learn the nav structure, which also helps them reference paths accurately in support tickets.

08 — Component Design

Component Library

Built a focused component set for the new sidebar system — icons, logo lockup, search states (empty, active, results, no-results), and menu item states (default, hover, active, collapsed/expanded).

All menu item states — default, hover, active L1, active L2, active L3, collapsed

⚖️ Key Trade-off: Real-time Search vs. 3-Character Minimum
Engineering advocated for real-time search to feel "modern." Testing showed 1–2 character inputs returned 47+ results, creating scanning overhead. Decision: 3-character minimum with informative placeholder messaging. Result: search time reduced from 15s → 6s.

09 — Validation

Usability Testing — Final IA

After raising the minimum search character count to 3 and retesting with users, we observed significant improvement in both discoverability and time on task. The combination of improved IA + 3-char search eliminated most navigation friction for returning users.

TaskDiscoverabilityDrill-DownSearch (3-char min)
Open Survey Review Easy 0m 20s 0m 6s ↓
Open Planogram UPC Report Easy 0m 24s 0m 4s ↓
Open IR Self Quality Check Easy 0m 18s 0m 7s ↓

Discoverability improved significantly for returning and knowledgeable users. New users still found discovery somewhat challenging — a known trade-off acknowledged in the V2 roadmap, where contextual onboarding was prioritized.
